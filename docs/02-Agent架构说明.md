# RiskCopilot · Agent 架构说明

> 本文回答一个具体问题：**我们现在的结构形式，算不算 Agent / 多 Agent 用法，还是只是 workflow（同一任务内的多段 prompt 串联）？**
> 结论先行：**是多 Agent 用法，且形成完整任务闭环。** 下文逐条对照评审判据，每条都指到真实可运行的代码位置（`demo/` 目录），不是 PPT 空话。

## 二、四个 Agent 的职责 / 输入 / 输出 / 工具 / 决策逻辑

### 1. 意图理解 Agent（`agent_intent.py`）
- **职责**：自然语言任务 → 结构化意图。
- **输入**：用户一句话（如"600519 和 000651 哪个财务更干净"）。
- **输出**：`{companies:[{name,code}], intent_type, focus, restated, source}`。
- **工具/决策**：LLM 解析为主（认得公司名→代码），正则抓 6 位代码兜底，域外问题（`out_of_scope`）礼貌拒答不硬套。`source` 字段如实标注是 LLM 解析还是规则兜底。

### 2. 总控编排 Agent（`agent_orchestrator.py`）—— 项目组长
- **职责**：像审计项目组长一样，对每个标的**按风险分级、自主决定查多深**。
- **输入**：自然语言任务 + 三个依赖注入的能力回调（`resolve_fn`/`deepdive_fn`/`debate_fn`）。
- **输出**：`{restated, intent_type, targets:[各标的完整结果], summary, compare?}`，每个标的带 `reached`（升级到哪层）+ `trail`（决策轨迹）。
- **决策逻辑（这是自主编排的灵魂）**：
  - 粗筛永远先做（成本最低）；
  - `score==0 且 GNN 不高` → **止步粗筛**（不深挖、不谈追责，避免越权）；
  - 有信号亮起 → 升级**深度研判**；
  - `score>=4 或 GNN 高 或 命中监管红旗` → 升级**控辩互搏**；
  - 对抗后仍判高/极高 → 标记**追责测算**。
  - **同一套代码，清白公司止步、高危公司一路查到追责——不同输入走出不同编排路径，每步都有 `reason` 可解释、可审计。**

### 3. 深度研判 Agent（`agent_deepdive.py`）—— ReAct 闭环
- **职责**：会读公告、会推理的研判副驾。
- **输入**：代码 + 公司档案 + 确定性信号 rows + GNN 分。
- **输出**：`{plan, trace, redflags, verdict, actions, effectiveness, ...}`。
- **工具/决策逻辑**：
  - `plan()` **运行时按局面自主规划**调哪些能力（`agent_deepdive.py:225`）——茅台清白只跑信号+防御性核查即止步，康美高危则 signals→gnn→materials→penalty→synthesis 全开；
  - 读材料时 LLM 提炼的定性红旗**必须匹配到真实公告标题**才放行，匹配不上直接丢弃（防幻觉，`agent_deepdive.py:100`）；
  - LLM/网络失败**全程降级为规则版**，demo 不崩。

### 4. 控辩互搏 Agent 组（`agent_debate.py`）—— 名副其实的多 Agent 协同
- **职责**：三个立场对立的 Agent 就同一套硬证据对抗，靠辩论收敛出更少误报的结论。
- **角色与交互链**：
  - 控方（Prosecutor）：最审慎审计视角，提出风险指控；
  - 辩方（Defender）：**读控方输出**，逐条找合理经营解释（辩方越强=系统越不误报）；
  - 裁判（Judge）：**读控辩双方输出**，逐条裁定 sustained/mitigated/uncertain + 最终风险画像。
- **这是与 workflow 的分水岭**：后一个 Agent 的 prompt 真实消费前一个 Agent 的输出，是角色间对抗，不是三段独立 prompt。

## 三、为什么这不是"同一任务内的多段 prompt 串联"

老师担心的 workflow 是"写死的 A→B→C 顺序调 LLM"。两个硬性差异证明我们不是：

1. **规划是运行时决定的，不是写死的**：`plan()`（`agent_deepdive.py:225`）与 `_run_one` 的升级判断（`agent_orchestrator.py:78/97/119`）都是**数据驱动的条件分支**。不同输入 → 不同调用集合与不同编排路径。可以现场演示：茅台走出"止步粗筛"、康美走出"一路升到控辩+追责"，两条轨迹用同一套代码。

2. **存在真正的 Agent 间信息流与对抗**：debate 的辩方吃控方、裁判吃控辩，orchestrator 把深研的红旗喂给控辩。这是**多 Agent 协同**（agents 之间传递上下文、相互制衡），而非单 Agent 顺序调工具。

此外还满足赛道对"进入真实业务场景"的要求：真实 A 股数据、真实巨潮公告、逐条可溯源、带追责测算，非单点问答。

---

## 四、合规与边界（呼应赛道"避免越权决策"）

- 硬信号是 ground truth，LLM 只能补充解释、**不得推翻事实**；裁判不得把已发生的事实"辩没"（`agent_debate.py:16` 铁律）。
- 分级升级本身即"不越权"：低风险不深挖、不谈追责。
- 所有结论只做风险提示与核查建议，**不给"一定造假"定性，不替代机构与司法决策**（每个 Agent 结尾强制合规声明）。

---

## 五、编排层选型（已确认）

**编排层采用纯 Python 依赖注入编排**（即本文档描述的这套）：总控 Agent 按风险分级自主升级，`resolve_fn`/`deepdive_fn`/`debate_fn` 作为能力回调注入，编排层与模型层解耦、模型可插拔。

选此路线的理由：
- **可运行、可自证**——`demo/` 已端到端跑通，评审可现场复现，不依赖任何外部托管平台账号；
- **纯逻辑、可离线测**——编排不绑具体数据源或聊天室框架，迁移成本低；
- 参赛面向**无界应用**赛道，编排自主性与任务闭环由代码本身证明，无需额外的多 Agent 托管框架背书。

> 说明：本项目早期曾考虑将编排层托管到聊天室式多 Agent 框架，现已放弃该路线，统一以 Python 编排为准。PPT 与介绍文档均已同步。
